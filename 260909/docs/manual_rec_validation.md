# Rec操作による保存への改修と検証（2026-09-09）

ビルド済みアプリは `build/DualHolo.app`、バージョン1.1。
カメラ設定を書き換えるコードは追加していない。
実カメラの重複起動を防ぐ排他ロックは維持し、今回の実行検証はすべて `--simulate` で行った。

## 保存方式

画像受付はRecorderのRec開始・停止と同じmutexで直列化する。
受付した時刻をCSVに記録し、カメラごとの全受信画像をFIFOで保存する。
ペア不成立やGUIの描画遅延を理由に録画画像を捨てない。
Rec OFFでは画像の履歴を貯めず、保存ジョブを生成しない。
Stopと終了は新規受付を閉じ、受付済み画像の保存と枚数照合が終わってから録画を完了する。

## 実行結果

| 検証 | 結果 |
|---|---|
| CMake Releaseビルド | 成功、警告なし |
| CTest | 1/1成功、1.28秒 |
| 光伝搬の数値テスト | 3/3成功、1.426秒 |
| 起動後1秒、Rec操作なし | TIFF 0枚 |
| 0.9秒のRec区間 | cam0/cam1各9枚、合計18枚 |
| Rec中にアプリ終了 | cam0 10枚、cam1 9枚、受信した19枚すべて保存 |
| GUIで3分間、Rec操作なし | 各カメラ1801枚受信、保存0枚 |
| GUIでR開始・STOP RECクリック | cam0 458枚、cam1 457枚を保存 |
| GUIでRECクリック・R停止 | 各11枚保存 |
| GUIでQ終了 | 正常終了、保存待ち0、エラーなし |

全ての保存画像についてCSVの保存受付時刻がRec区間内にあること、ファイルの存在、受付・保存・ファイル枚数の一致を検査した。
GUI操作検証の合計はcam0 469枚、cam1 468枚で、欠落・不完全画像・ディスク待機は0。
Rec区間の境界が2台の受信の間に来た場合の1枚差も、片方の画像を捨てず保存できている。

CTestには、相手のないフレーム、複数回のRec、終了時の書き切り、8/16 bit TIFFの画素完全一致、欠落の記録を含む。
32 MiBの1枚を32 MiBキューへ入れる試験では、保存を捨てず取得側が待機し、その画像を保存できた。
2448 × 2048の16 bit画像を2スレッドから各8枚投入する試験でも全16枚を保存できた。
保存先がディレクトリでない場合は保存エラーとして停止し、正常終了とは扱わないことを確認した。

光伝搬では4096 × 4096の中央配置、実数・複素数の平均値埋め、サイズ超過の拒否を検証した。
z=0で入力強度を再現すること、均一な入力強度が各伝搬距離で保たれることも検証した。

## 検証範囲

実機での長時間連続録画とストレージの持続書込速度は今回測定していない。
キューが満杯なら画像を捨てずに取得側を待つが、その間のSDK・USB側の欠落まで保証するものではない。
発生したフレーム欠落・不完全画像・ディスク待機は画面と実行要約へ記録する。

再現用テストは `tests/test_core.cpp`、`registration/test_optical_padding.py`。
実行ログとCSVの検査結果は `validation/manual_rec/integration_results.json`、CTestのログは `build/Testing/Temporary/LastTest.log` にある。
